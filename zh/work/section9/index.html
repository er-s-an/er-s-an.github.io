AGENT 评测 · 故障响应

让修复 Agent 的 Agent，也接受可核验的评测。

Section9 把运行证据、代码、受控执行和业务验收接成一条故障响应工作流。我实现了同案配对展示，对比单 Agent 与多 Agent 的任务结果，同时保留失败，不预设 Agent 越多越好。

以业务结果为中心的评测

Harness 在同一任务规格下配对单 Agent 基线与多 Agent arm，记录任务状态、实际耗时、Token、未知结果和源码身份，而不是凭一段看似合理的对话判断成功。

Prompt、成本、循环与复合故障四类场景都在最终源码版本上完成了一组配对闭环，共 8 次 arm run；早期失败也保留在证据中。

受控修复，而不是无限自治

Section9 实现了权限授予、租约、fencing、取消、独立验收和不可变运行身份。修复执行后要重新检查受影响的业务行为，迟到响应和过期权限不能覆盖更新的运行。

只读展屏把真实任务事件投影为可检查的办公室与证据抽屉。界面负责解释系统，原始事件和验收报告才是事实来源。

经得起追问的证据链

最终复合故障组中，两侧都通过业务验收：单 Agent 用时 25.007 秒、消耗 5,338 Token；多 Agent 用时 31.905 秒、消耗 7,183 Token。这是实测记录，不是多 Agent 更优的结论。

OpenTelemetry、Langfuse、浏览器验收、源码哈希和原始运行文件，让实验从界面到执行证据都能被复查。

实验设置

最终版本的四类固定场景各有一组正常配对，使用远程模型推理。样本量不足以证明统计稳定性或任何一种架构的普遍优势。
